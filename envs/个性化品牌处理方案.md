# Desktop 个性化品牌处理方案

## Summary

本文记录 Desktop 品牌定制的当前实现和依赖关系，供后续升级 DSH 核心、合并上游改动或处理同文件冲突时使用。升级时应先保留新版本的功能改动，再按本文的配置、客户端品牌插槽、Electron 展示、图标资源和安装包发布链逐项恢复品牌能力。品牌定制集中在 Desktop 环境配置和应用集成层；只有侧栏品牌名称与图案使用 DSH 客户端的官方品牌插槽。任何恢复都必须保持应用身份、用户数据目录、更新身份和既有 DSH 默认行为不变。

## 适用范围与目标

品牌化改变 Desktop 用户看到的名称、图案和版本化安装文件名，同时保留 DSH 的应用身份和已有用户数据；本节界定恢复范围和判断冲突的原则。

### 目标状态

- 构建入口只读取显式选择的 `envs/<环境名>/config.json`，不把其他环境的品牌配置合并进构件。
- `desktop.branding` 独立于 `desktop.updates`，由 `displayName`、`iconSet` 和可选 `artifactNameBase` 描述品牌。
- `local` 和 `hxfl` 使用显示名称“金租办公”以及 `hxfl` 图标套装；`superbpm` 未配置品牌时继续使用 DSH 默认品牌。
- 默认 DSH 品牌继续使用 `DeepSeek Harness`、`dsh` 图标套装和 `deepseek-harness` 文件名前缀。
- 品牌名称不改变 `appId`、`dsh` 协议、DSH_HOME、用户数据路径、诊断日志路径、更新 distribution 或 channel。
- 版本化安装包、自动更新负载、元数据、上传计划和版本发现使用同一个 `artifactNameBase`。

### 冲突解决原则

上游 DSH 核心的行为、接口和测试优先保留；品牌定制只补回这些行为之上的环境选择和品牌投影。遇到同一文件冲突时，不要整体选择“ours”或“theirs”，而要先识别上游新功能，再把品牌责任放回当前承担相同责任的模块。若上游移动或重命名模块，应按本文描述的职责寻找新位置，不应为了复刻旧文件布局而恢复过时实现。

## 品牌配置与资源约定

环境文件选择品牌，资源套装提供与平台对应的图像；解析器将两者规范化后交给构建链。恢复时先确认这项输入输出约定，再修改消费它的代码。

### 环境配置

当前 [local 配置](local/config.json) 和 [hxfl 配置](hxfl/config.json) 设置 `displayName` 为“金租办公”并选择 `iconSet: "hxfl"`。`hxfl` 是一个完整的命名环境，可使用 `--config-env hxfl` 选择；它沿用当前 `superbpm` 环境的插件市场和更新服务地址。`local` 保留自己的本地服务地址，因此两个环境不能互相替代。

```json
{
  "schemaVersion": 1,
  "environment": "hxfl",
  "desktop": {
    "branding": {
      "displayName": "金租办公",
      "iconSet": "hxfl"
    },
    "updates": {
      "distribution": "dshwork",
      "checkUrl": "https://hxai.superbpm.com/app-api/v1/desktop/updates/check",
      "channel": "stable",
      "feedOrigins": ["https://hxai.superbpm.com"]
    }
  }
}
```

`artifactNameBase` 可以省略；配置了非空 `displayName` 时，默认文件名前缀跟随显示名称。名称或图标字段缺失、为 `null` 或为空字符串时使用对应的 DSH 默认值；显式提供非法字段、未知图标套装或不安全文件名前缀时，构建必须失败，不能静默回退。

### 图标套装

图标套装以 `apps/desktop/resources/brand-sets/<iconSet>/` 为唯一资源根目录。每套完整资源都包含以下文件；构建入口在生成构件前检查文件存在、可读且非空。

| 文件 | 用途 |
| --- | --- |
| `sidebar-mark.svg` | 客户端侧栏标记；SVG 作为构建时内嵌的数据 URI，使用侧栏文字颜色渲染。 |
| `icon-macos.png` | macOS 应用图标源文件，由 electron-builder 生成应用图标资源。 |
| `icon-windows.png` | Windows 应用图标源文件。 |
| `tray-windows.ico` | Windows 托盘图标，包含多种显示尺寸。 |
| `installer/brand.png`、`brand-2x.png` | Windows 安装器浅色品牌图及高分辨率版本。 |
| `installer/brand-dark.png`、`brand-dark-2x.png` | Windows 安装器深色品牌图及高分辨率版本。 |
| `installer/uninstaller-sidebar.png` | Windows 卸载界面侧栏图。 |

`dsh` 套装保留原 DSH 资源；`hxfl` 套装使用用户提供的华夏金租红色图案，只包含图案，不带“华夏金租”或“金租办公”文字。应用名称由 `displayName` 独立决定。新增品牌时应新增一套完整资源，再由目标环境引用套装名；不要用本机绝对路径、在构建时下载图标，或只替换某个平台的单个文件。

## 实现链路与文件职责

品牌配置沿一条链路从环境文件进入客户端构建、Electron 应用和发布工具。DSH 核心升级时，下面每一层都要找到新版本中的对应职责并确认没有断链。

| 层 | 当前主要文件 | 需要保留的行为 |
| --- | --- | --- |
| 品牌解析与资源验证 | [`desktop-branding-environment.mjs`](../apps/desktop/scripts/desktop-branding-environment.mjs)、[`package-target.ts`](../apps/desktop/scripts/package-target.ts) | 读取所选环境并检查环境名、schema、品牌字段及完整资源套装；在版本发现和打包前解析规范化品牌。 |
| 客户端品牌插槽 | [`Brand.tsx`](../packages/client/ui-brand-official/src/client/Brand.tsx)、[`client-build-environment.ts`](../scripts/client-build-environment.ts)、[`families.ts`](../scripts/release/families.ts) | 官方侧栏品牌组件接受构建时名称与 SVG 标记；品牌名称缺省时保留官方字标，图标缺省时保留鲸鱼标记；标记按当前文字颜色绘制。 |
| Electron Builder 配置 | [`electron-builder-config.mjs`](../apps/desktop/scripts/electron-builder-config.mjs)、[`electron-builder.config.d.mts`](../apps/desktop/electron-builder.config.d.mts) | `productName`、平台应用图标、托盘资源、NSIS 图片和 `artifactName` 使用选中品牌；`appId`、`dsh` 协议及更新配置保持固定。 |
| Desktop 运行时 | [`main.ts`](../apps/desktop/src/main.ts)、[`locale.ts`](../apps/desktop/src/locale.ts)、[`preload-welcome.ts`](../apps/desktop/src/preload-welcome.ts)、[`welcome-window.ts`](../apps/desktop/src/welcome-window.ts) | 系统菜单、欢迎页和中英文壳文案使用显示名称；日志和用户数据位置仍使用原 DSH 路径。 |
| Windows 安装器 | [`strings.nsh`](../apps/desktop/installer/strings.nsh)、[`prepare-windows-installer.ps1`](../apps/desktop/scripts/prepare-windows-installer.ps1)、[`render-tray-icon.ts`](../apps/desktop/scripts/render-tray-icon.ts) | 安装/卸载提示使用选中的应用名；安装器读取套装图像；默认 DSH 托盘源仍属于 `brand-sets/dsh`。 |
| 文件名和更新发布 | [`desktop-build-version-discovery.ts`](../apps/desktop/scripts/desktop-build-version-discovery.ts)、[`package-macos.ts`](../apps/desktop/scripts/package-macos.ts)、[`private-desktop-update-artifacts.mjs`](../apps/desktop/scripts/private-desktop-update-artifacts.mjs)、[`desktop-upload-plan.ts`](../apps/desktop/scripts/desktop-upload-plan.ts)、[`upload-target.ts`](../apps/desktop/scripts/upload-target.ts) | 本地/远端版本发现、macOS 最终整理、更新元数据校验和上传计划使用相同文件名前缀；上传前核对构建记录中的环境和品牌。 |
| 环境和行为测试 | [`desktop-branding-environment.spec.ts`](../apps/desktop/tests/desktop-branding-environment.spec.ts)、[`installer-packaging.spec.ts`](../apps/desktop/tests/installer-packaging.spec.ts)、[`main-startup.spec.ts`](../apps/desktop/tests/main-startup.spec.ts)、[`browser-plugin.client.spec.tsx`](../packages/client/ui-brand-official/tests/browser-plugin.client.spec.tsx) | 覆盖默认值、环境隔离、资源完整性、客户端插槽、应用身份、用户数据路径和安装包配置。 |

### 客户端侧栏名称与图案

Desktop 在官方客户端构建前将 `displayName` 传入 `DSH_CLIENT_BRAND_NAME`，并将 `sidebar-mark.svg` 编码为 `DSH_CLIENT_BRAND_MARK` 的 base64 SVG 数据 URI。构建环境验证这两个字段后，Vite/tsdown 将值编译进客户端品牌组件；组件以 CSS mask 的透明度作为图形，并以 `currentColor` 显示。若上游调整了官方品牌组件或构建环境字段，必须同时迁移生产者、验证器、进程环境投影和客户端消费者。

客户端官方发布记录也包含其完整构建环境和产物摘要。升级构建配置时，必须保持品牌字段在官方构建环境、构建记录和校验路径中一致；不能只修改组件并绕过构建记录验证。

### 显示名、应用身份和用户数据

Electron Builder 使用品牌显示名作为 `productName`，因而应用包名和系统展示名会改变。主进程在 Electron ready 前显式将 `userData` 和 `sessionData` 固定到原有 `appData/DeepSeek Harness` 目录，日志仍写入原有 `DeepSeek Harness` 日志目录。`appId` 是安装升级身份和 macOS Bundle ID 的组成部分，必须保持原值。

Windows 安装器使用构建元数据中的应用名显示安装和卸载提示。更新安装器、目录名称、快捷方式文字或图标时，只应改变展示信息；不要修改 NSIS 升级 GUID、应用标识、协议、用户数据目录或更新分发配置来实现视觉品牌化。

### 版本化文件名和更新链路

electron-builder 生成 `<artifactNameBase>-<version>-<os>-<arch>[-unsigned|-internal].<ext>`。macOS 应用整理、私有更新元数据校验、上传规划、本地制品扫描和远端版本发现均以同一个 `artifactNameBase` 匹配文件。

成功构建记录将 `configEnvironment` 和规范化 `branding` 与目标、版本及更新目标一起保存。上传命令可以通过 `--config-env` 指定环境；上传器会重新解析所选品牌，并拒绝与构建记录不一致的文件。更新 payload URL 对中文文件名执行 URI 编码。

稳定下载别名 `dsh-latest-*`、更新 channel YAML 文件名、更新服务协议、签名/公证流程和差分更新校验保持现状。任何上游改动如果移动了这些处理函数，必须重新确认命名生成、元数据校验、远端发现和上传验证使用同一个规范化品牌值。

## 升级 DSH 核心时的冲突解决步骤

合并 DSH 核心升级前，先把品牌实现作为一组有边界的本地改动保存；合并上游后按责任层恢复品牌行为，不要把打包输出或整个旧实现复制回新版本。

1. **确认升级前基线。** 检查工作区并保存当前品牌实现、`envs/local/config.json`、`envs/hxfl/config.json` 和 `apps/desktop/resources/brand-sets/hxfl/`。确认新环境文件、图像资源、Desktop 代码、客户端包、测试和本方案都进入同一变更记录。
2. **先完成上游核心改动。** 对冲突文件逐个恢复新版本的功能、类型、依赖和测试。不要为减少冲突直接选择整个旧版 Desktop 文件或整份旧版 `Brand.tsx`。
3. **重新定位职责。** 若上游移动模块，按“品牌解析”“客户端品牌插槽”“Electron 运行时”“安装器资源”“发布文件名”查找新 owner；先调整品牌逻辑所在位置，再更新它的所有消费者。
4. **恢复环境读取。** 确保 `--config-env hxfl` 与 `DSH_CONFIG_ENV` 都选择相同的 `$DSH_CONFIG_ENV_DIR/hxfl/config.json`。品牌必须在版本发现、官方客户端构建和 electron-builder 启动前解析，并且只传递规范化结果。
5. **恢复客户端插槽。** 保留官方品牌组件对配置名称和图案的支持，以及没有品牌配置时的 DSH 字标/鲸鱼回退。更新生产者和消费者时，同步更新构建环境验证、客户端构建记录及对应测试。
6. **恢复平台资源映射。** `dsh` 和 `hxfl` 套装都必须保持完整；Windows/macOS 图标、Windows 托盘和五张安装器 PNG 都应通过资源解析器引用所选套装。新增、改名或删除资源文件时，同时更新完整性校验、Builder 映射、安装器准备脚本和测试。
7. **恢复展示名但固定身份。** 检查 `productName`、Electron 菜单、欢迎页、关于信息、托盘和 NSIS 文案；同时确认 `appId`、`dsh` scheme、DSH_HOME、`userData`、`sessionData`、日志路径及更新目标仍保持既有值。
8. **逐一恢复文件名消费者。** 用一个规范化 `artifactNameBase` 驱动 Builder、macOS 整理、更新元数据校验、上传规划、本地扫描和远端版本发现。检查完成记录携带环境与品牌，并检查上传会重新解析和比较它们。
9. **更新测试和环境说明。** 保留默认值、空值、非法值、未知/不完整图标套装、环境隔离、品牌 UI、稳定目录、安装器身份、命名和上传匹配等行为测试；同步更新本方案和 Desktop README 中受影响的字段/用法。
10. **从低成本到完整打包验证。** 先运行配置解析、客户端品牌、Builder、更新命名和上传测试，再运行类型检查、文档检查、OpenSpec 校验，最后至少对目标平台使用明确的 `--config-env hxfl` 构建内部产物并检查应用名、图标和文件名。

若升级后无法找到某个旧文件，应按其责任定位新实现并把功能迁过去，不要恢复旧目录结构。若同一个文件中上游和品牌改动分别位于不同函数，尽量保持上游函数并将品牌解析作为显式参数传入，避免复制隐式默认值或新增第二份品牌状态。

## 必须保持的兼容性约束

以下约束决定定制是否仍然可以安全升级和发布；任何冲突修复都应逐条验证，而不是只确认构建命令退出成功。

- **默认路径：** 未选择命名环境，或品牌字段缺失/为空时，使用 `DeepSeek Harness`、`dsh` 图标套装和 `deepseek-harness` 文件名前缀。
- **环境隔离：** 构件只读取所选环境；`local` 的 localhost 服务地址不得复制到 `hxfl`，`hxfl` 和 `superbpm` 的生产服务地址也不得混入 `local` 构件。
- **失败方式：** 环境配置无效、品牌值不安全、图标套装未知或资源缺失时，在产物生成前失败，不生成部分构件，不以另一套图标偷偷替换。
- **应用身份：** `appId`、Bundle ID、NSIS 升级标识和 `dsh` scheme 不随显示名称或图标变化。
- **本地数据：** `userData` 和 `sessionData` 保持原 `DeepSeek Harness` 路径，日志目录也不随品牌迁移。
- **发布一致性：** 构建、元数据、文件名、版本发现和上传计划都使用同一个品牌记录；上传品牌与构建记录不匹配时失败。
- **稳定更新路径：** `dsh-latest-*` 别名、channel 文件名、distribution、channel、feed 协议和签名身份保持不变。
- **客户端回退：** DSH 默认配置继续显示官方字标和鲸鱼图案；品牌名称及侧栏图案只能在选择了相应配置时覆盖默认插槽。
- **素材所有权：** `hxfl` 图案资源保持不含文字；品牌名称只通过配置显示，不把文字烘焙进应用图标或侧栏图案。

## 验证清单

验证应覆盖配置、客户端、应用包和发布消费者。当前定向验证使用以下命令；升级后根据变动平台补充 Windows 构建或更新发布检查。

```sh
pnpm exec vitest run apps/desktop/tests/desktop-branding-environment.spec.ts apps/desktop/tests/installer-packaging.spec.ts apps/desktop/tests/private-desktop-update-artifacts.spec.ts apps/desktop/tests/desktop-upload-plan.spec.ts apps/desktop/tests/desktop-build-version-discovery.spec.ts apps/desktop/tests/main-startup.spec.ts packages/client/ui-brand-official/tests/browser-plugin.client.spec.tsx
pnpm run typecheck
pnpm run verify-translation-pairing apps/desktop/README.md
openspec validate configure-desktop-environment-branding --strict --no-interactive
./build-macos.sh --internal-dmg --config-env hxfl 0.2.1-alpha.2
```

打包完成后检查 `.app` 的 `CFBundleDisplayName` 和 `icon.icns`，再确认版本化 DMG/ZIP 使用所选 `artifactNameBase`。Windows 变更还要核对安装器提示、应用图标、托盘 ICO、安装/卸载图片和签名/升级身份。若客户端构建记录的环境摘要与所选品牌不一致，先清理并重建对应客户端产物，不能绕过记录校验。
