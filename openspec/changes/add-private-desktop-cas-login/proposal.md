# Proposal: dsh-pro-auth 独立插件与 CAS 企业登录

## Why

企业部署需要员工通过 CAS 2.0 单点登录后才能使用 DSH 桌面客户端，并让客户端取得可信的用户信息和应用登录凭据；登录流程不能依赖员工电脑接收回调。认证实现作为本仓库 `pro/dsh-pro-auth/` 下的插件维护，按功能模块隔离私有代码，并在模块内部复用公共实现、区分企业配置，以减少上游升级的合并冲突和重复适配。

## What Changes

- 首期完成 DSH Host、CAS 与 `sso-cas/dsh-auth` 的登录闭环：发起登录、验票、确认本次客户端登录、领取应用凭据、获取当前用户及退出。首期不调用 TokenHub，也不检查或模拟 TokenHub 用户、权限与额度；有效 CAS 身份完成本次登录确认后即可通过登录准入，模型使用仍依赖单独配置的模型凭据。
- 新增企业登录服务，接收浏览器从 CAS 返回的云端 HTTPS 回跳，通过 CAS 2.0 `/serviceValidate` 验票并建立应用登录态。DSH 使用系统浏览器完成登录，主动查询授权结果并凭本次登录尝试的私密证明领取凭据，无需本机回调端口。
- 每次登录由 DSH Host 创建唯一 `request_id` 和随机私密 `verifier`，向服务端登记请求及 `verifier` 的 SHA-256 摘要。服务端按请求关联浏览器授权和客户端领取，不按 IP、用户名或设备的最新请求分配结果；公开登录编号或授权链接不能单独用于领取凭据。
- DSH Host 保存应用凭据并向界面提供不含凭据的登录状态和用户信息。用户标识取自服务端验票结果；姓名、部门等扩展资料仅在真实数据源支持时提供。票据和令牌不得进入模型上下文、会话日志或界面展示数据。
- **BREAKING（仅启用强制企业认证的发行版）**：已有 API Key、DeepSeek 账号或“跳过”入口不再足以进入工作区。桌面启动和 Host 业务访问共同检查企业登录态，覆盖业务 RPC、文件访问及流连接；企业认证与模型凭据分别管理。未启用企业认证的发行版保留现有行为。
- 新建名为 `dsh-pro-auth` 的 DSH Host / Client 插件，源码、测试和构建定义在本仓库 `pro/dsh-pro-auth/` 维护，不建立独立 Git 仓库或子模块。`pro/` 的一级目录按功能插件划分；未来的 `pro/dsh-pro-usage/` 可与认证插件平级，本次不创建该模块。
- `pro/dsh-pro-auth/share/` 保存共用认证实现与协议；`pro/dsh-pro-auth/hxfl/`、`pro/dsh-pro-auth/superbpm/` 保存各企业非敏感配置、装配入口及必要差异适配，复用 `share/`，不复制整套认证实现。企业目录代表不同部署，不引入运行时多租户切换；密钥由部署环境或凭据存储提供。
- 插件可单独构建、打包，以 Cordis bundle 提供装配。开发时由选定 DSH profile 和 overlay 解析并启用插件及企业配置；源码位于仓库中不意味着自动启用。Desktop 打包时纳入插件产物及选定企业配置，在 Desktop 专用 profile 中启用；未选择企业认证的发行版不装配该插件，也不要求提供企业认证配置或密钥。
- 优先使用现有扩展点实现零原生代码改动；设计阶段先验证完整准入与打包装配能力，再列明无法由插件实现的缺口。只有必要缺口才提出通用、最小的上游扩展，不将 CAS 或企业特有判断写入上游，不复制桌面主入口、Connection 实现或修改 agent-loop。企业认证配置缺失或插件加载失败时，要求认证的发行版不得降级为免登录。

### 客户端请求关联与结果交付

本节的“授权”仅指用户同意将本次登录结果交付给指定 DSH 客户端，不表示 TokenHub 已授予业务权限或模型额度。

借鉴原生 Platform 登录对安装标识、登录尝试及兑换证明的区分，将其本地回调交付改为客户端主动查询。轮询与浏览器授权的分离参考 [RFC 8628 设备授权流程](https://www.rfc-editor.org/rfc/rfc8628.html)，由 `dsh-auth` 提供适配，不要求 CAS 实现 OAuth，也不将本方案直接声明为完整的 RFC 8628 实现。

| 标识 | 生命周期与职责 |
|---|---|
| 应用标识 | 区分接入应用；CAS 注册云端登录服务，不为每台电脑注册服务 |
| `device_id` | 每个安装实例生成并保存，用于关联安装，不作为认证凭据或可信硬件身份 |
| `request_id` | 每次新登录生成，用于定位本次尝试；重试创建沿用原值 |
| `verifier` | 每次登录随机生成并由 Host 私密保存，用于证明查询、取消和兑换请求的领取权限；不进入浏览器授权链接 |

1. DSH 向 `dsh-auth` 提交应用与安装标识、`request_id` 和摘要，取得浏览器授权链接、有效期、短确认码及查询间隔。重复创建只能在绑定信息和证明匹配时返回原请求，冲突请求不得覆盖原记录。
2. 浏览器打开授权链接；服务端校验请求，建立绑定该 `request_id` 的浏览器授权上下文，再跳转 CAS。CAS 的 `service` 使用固定云端 HTTPS 回调；请求关联由服务端保存，不依赖 CAS 回传自定义字段。
3. 浏览器携 ST 回到云端后，服务端恢复授权上下文并向 CAS 验票。网页展示经验证的账号、短确认码及客户端描述，用户核对与 DSH 显示一致后确认或拒绝授权；机器名称仅作提示。未关联、已失效的回跳不得批准请求，客户端提交的用户名不得作为身份依据。
4. 首版对同一浏览器会话中尚未完成的 CAS 往返串行处理；第二次请求明确提示已有登录进行中，不覆盖第一条关联。不同浏览器会话可并发登录；已有浏览器登录态时仍须确认指定请求，不自动批准该用户的其他请求。
5. DSH 使用 `request_id` 和私密证明主动查询，遵守服务端查询间隔、限流和退避；已授权后使用 `verifier` 兑换应用凭据与用户信息。私密证明仅通过 HTTPS 请求体或认证头传递，不写入 URL、普通日志或界面状态；只有公开 ID 的请求不能查询授权详情或领取结果。
6. 服务端原子地完成一次兑换。首版在兑换已完成但响应丢失时要求重新登录，不通过重复兑换重新发放令牌；浏览器已有 CAS 会话时可复用单点登录。Host 仅接纳当前尝试的结果，取消或新请求发起后到达的旧结果不能覆盖当前身份。

服务端保存请求绑定信息、摘要、浏览器授权上下文、验票所得用户标识、状态及截止时间。状态包括等待认证、等待确认、已授权、已兑换及取消、拒绝、过期；取消或过期后不得因迟到回跳重新授权。兑换与取消的并发次序由原子状态更新决定；取消先成功则兑换失败，兑换先完成则按已兑换处理，客户端放弃本地接纳不能声称服务端凭据已撤销。

多实例部署使用共享请求存储和原子状态更新，不依赖单个服务进程的内存分配登录结果。该记录关联的是一次授权尝试，不要求服务端知道客户端公网地址或主动连接客户端；具体存储选型和接口字段由设计文档确定。

## Capabilities

### New Capabilities

- `enterprise-cas-login`: CAS 2.0 固定云端回跳、逐次客户端请求与私密证明、浏览器授权关联、限流轮询、原子一次性兑换、可信用户信息和登录生命周期。
- `desktop-enterprise-admission`: 企业发行版的强制登录、桌面工作区放行、Host 业务访问控制，以及登录失效后的访问收回。
- `enterprise-deployment-composition`: 仓库内 `pro/<插件名>/` 功能模块组织、`dsh-pro-auth` 内部的 `share/` 共用实现及企业配置、开发时按 profile 启用、Desktop 打包预装及上游版本兼容验证。

### Modified Capabilities

无。当前项目尚无已登记的 OpenSpec 规格；上述能力将新增规格，其中包含对现有桌面准入行为的变更。

## Impact

### 首期接口职责与后续企业授权

- `dsh-auth` 首期向 DSH Host 提供登录请求创建、状态查询、取消、凭据兑换、当前用户及应用会话退出能力；接口路径、响应字段和登录有效期在设计阶段确定。Host 处理凭据，Client 界面只接收用户资料、登录状态和必要的授权交互信息。
- 首期应用凭据用于访问 `dsh-auth` 的登录与用户接口，不是模型 API Key，也不是 TokenHub 令牌。客户端不得把登录成功展示或解释为 TokenHub 权限、额度检查通过，接口不得返回虚构的权限或额度结果。
- 后续由 `dsh-auth` 对接 TokenHub，要求用户在 TokenHub 存在、具有使用权限且有可用 token 额度，方可使用受该授权控制的能力。TokenHub 的检查、凭据获取及失效处理属于后续变更，当前不新增空实现或默认放行的 TokenHub 授权接口；DSH 客户端不承担直接对接 TokenHub 的责任。

### 代码与部署

- 登录界面、用户状态、凭据管理、协议适配和准入策略归 `pro/dsh-pro-auth/` 所有，模块根维护包声明及构建入口。插件通过公开接口依赖 DSH；workspace、依赖锁定和检查范围的具体接入在设计阶段明确，不另建绕过 `dsh` profiles 的 Node 应用启动器。
- 企业构建从同一仓库提交取得 DSH、插件和选定企业配置，验证依赖解析、Host / Client 导出及最终产物。插件或选定企业配置缺失、版本不兼容时明确失败；检查 `hxfl` 与 `superbpm` 的配置不会相互混入发行产物。
- 零侵入可行性验证须覆盖原生欢迎页先于 Client 插件加载的路径、HTTP 与 WebSocket 准入、已建立连接的失效处理，以及 Desktop 预装包的解析与启用。现有 HTTP `connection/request` 监听器不覆盖 Gateway 的 WebSocket upgrade；部署配置解析也不等于预装链路已经接通。不能用界面遮罩或仅拦截模型调用代替强制准入，不能通过运行时替换内部方法规避缺失的公共扩展点。
- Desktop 恢复流程会禁用第三方 bundle；企业认证插件被禁用、卸载或加载失败时，企业发行版必须保留拒绝业务访问的能力，仅允许必要修复流程。发布前需验证该约束，不能把可选插件的存在作为唯一保护。
- 配套服务拟位于独立项目 `sso-cas/dsh-auth/`，沿用 Spring Boot 技术栈，管理逐次登录请求、浏览器授权、CAS 验票、凭据兑换和用户信息。插件 `share/` 负责请求标识与证明、浏览器启动、轮询及本地凭据管理，企业目录提供服务地址与适配配置。`sso-cas/app1/` 仅保留为 CAS 登录演示，不承担 DSH 登录或下游令牌兑换。本提案记录跨项目依赖，不创建或修改该项目文件。
- 测试 CAS 为 `https://sso.superbpm.com/cas`；新服务域名、精确 CAS 服务注册和 HTTPS 回跳地址需在部署设计中确定，不使用允许任意回调的规则。
- 当前 App1 使用 CAS 3.0 验票客户端，不能替代本功能的 CAS 2.0 联调证据。现有测试配置关闭后端单点注销，不能据此承诺退出 CAS 后 DSH 立即失效。
- 应用登录凭据与 CAS ST 分开管理，不更改 Agent Session 日志格式。新增凭据存储及其版本演进在设计阶段明确；本地传输认证继续保留。

### 升级兼容与验收

- DSH 接口适配、插件实现和企业配置在同一仓库提交中维护与回退。记录必要上游接入点，并执行打包、插件加载、桌面启动与准入兼容检查；私有功能集中于 `pro/` 可减少源码合并冲突，但不消除上游插件 API 变更带来的适配成本。
- 验证干净检出后的企业构建、缺失插件或企业配置时的失败提示、企业配置选择，以及未启用企业认证时普通 DSH 的检查和构建。验证最终 Desktop 安装包可加载内置插件，无需从源码目录或 Git 仓库取得代码；这不代表 CAS 登录支持离线。
- 验证真实 CAS 2.0 登录、已有 SSO 会话、用户信息、取消、超时、断网和重启；验证无效或重复票据、错误服务地址、跨客户端领取和过期登录尝试均被拒绝。
- 在未部署或未配置 TokenHub 的环境中完成首期登录、领取凭据、读取当前用户和应用退出；确认没有 TokenHub 调用、模拟业务权限或额度返回，且应用凭据不会被当作模型凭据使用。
- 验证同一出口 IP 下多个安装实例、同一账号多个客户端、同一浏览器多标签页、重复创建及错误证明不会串号或覆盖请求；公开链接不能领取凭据。验证并发兑换仅成功一次、取消与回跳竞态、兑换响应丢失后的重新登录、旧请求迟到以及共享存储下跨服务实例查询，并检查秘密不出现在 URL、日志或界面状态中。
- 验证 API Key、跳过入口、直接业务请求和流连接不能绕过准入；登录失效后按确定的生命周期策略处理现有连接及任务。覆盖未启用企业认证的发行版回归，并补充适用的 UI、会话快照和桌面演示证据。

### 非目标与待确认事项

- 本次不实现共享服务器上的员工数据隔离，不复制 DeepSeek 平台的充值或额度功能，不复用缺少源码和测试的旧本机回调 CAS 插件。
- TokenHub 用户、权限、token 额度和相关令牌获取均不属于首期验收，也不阻塞登录闭环。后续以 TokenHub 实际接口确定 `dsh-auth` 的接入方式，不预设接受应用凭据或 CAS 代理票据，不复用已验证的 ST；App1 仅作为演示应用。
- 设计前需确定登录有效期、续期与离线策略、应用退出与 CAS 单点退出的关系、失效时运行中任务的处置，以及同一电脑更换员工账号时本地数据的访问策略。
- 客户端强制准入约束受支持的企业发行版；若要求修改本地程序后仍无法访问企业资源，相关授权必须同时由受控服务端执行。
